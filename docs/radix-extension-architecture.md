# Netops Radix extension architecture

## Decision

`netops-toolkit` is a single local-first operator product with two projections:

1. a native Modulus extension hosted by Pares Radix; and
2. a standalone Tauri package for operators who do not run the Radix workbench.

They share one Svelte surface, one PX-governed operation model, and the same
native host-effect boundary. The standalone package is not a second network
automation implementation.

The public `plures/netops-toolkit-app` repository remains the end-user
distribution, release, and support surface. Extension source, governance, and
release-attestation CI belong in the `praxis-platform` monorepo alongside
`pares-radix`, PluresDB, Praxis, and Svelte-Ratatui.

## Current truth

The current release provides only a real local OpenSSH SOCKS5 bastion workflow.
It does not yet host a Radix extension, connect to PluresDB, evaluate PX
procedures, or run a Ratatui projection. This document does not advertise any
of those capabilities as shipped.

The existing local bastion profile format remains supported during migration.
No migration may delete or overwrite a user's profile or credential material.

## Target shape

```text
                    Svelte operator surface
                              |
          +-------------------+-------------------+
          |                                       |
   Pares Radix host                      Standalone Tauri shell
 native Modulus extension                 packaged for the workstation
          |                                       |
          +----------- shared projection ---------+
                              |
                       Svelte-Ratatui
                    (TUI build/projection)
                              |
                  PX procedure admission
                    + PluresDB decision ledger
                              |
                     verified host effects
                              |
          OpenSSH / native network transport / OS I/O
```

### Source and release ownership

The extension source belongs at a monorepo path such as
`crates/pares-radix/extensions/netops-toolkit`. It must use the native Modulus
extension package contract:

- `radix-extension.json` declares a versioned extension identity and requested
  capabilities.
- `host-effects.px` describes the bounded native effects that the host may
  execute after PX admission.
- `bundle.js` is the built UI asset.
- package and release evidence are generated by the existing deterministic
  native-extension packaging flow.

The public repository consumes only attested, immutable outputs. It must not
reimplement extension decision logic or maintain a second source-of-truth
network core.

### Capability boundary

The initial manifest should request only the capabilities needed for a real
operator session:

| Capability | Purpose | Boundary |
| --- | --- | --- |
| `workbench.views`, `workbench.commands`, `workbench.settings` | Operator UI integration | Workbench-only |
| `pluresdb.read`, `pluresdb.write` | Versioned, user-controlled operational records | PX-admitted opaque records only |
| `praxis.procedures`, `praxis.decision-ledger` | Safety policy and durable decision receipts | PX is the authority |
| `native.bastion.host-inspect` | Report an already-running bastion's bounded status | Host supplies verified facts |

Starting, stopping, or changing a bastion is a separate native host effect. It
must have an explicit manifest capability and a PX contract before it is
available to an extension. The extension never receives a raw Tauri `invoke`
handle, filesystem path, OpenSSH argument list, secret, or PluresDB store.

### Data and secret boundaries

- PluresDB owns durable inventory, settings, operation receipts, scan history,
  config metadata, and migration records.
- PX owns capability admission, safety decisions, lifecycle, and audit
  receipts; Rust is limited to verified transport and OS-I/O effects.
- Secrets remain in the operating-system credential store or a versioned,
  local user-controlled vault. UI and extension records carry opaque references
  only, never passwords, SNMP community strings, private keys, or raw
  configuration payloads.
- Existing `bastion-profiles.json` is imported copy-first into a versioned
  record. The importer records a receipt and leaves the source file intact
  until an explicit user-confirmed cleanup release.

## Svelte-Ratatui adoption gate

Svelte-Ratatui is the correct convergence route because it compiles a Svelte
surface to Ratatui widgets and offers a Tauri adapter. It is currently marked
pre-alpha, and its Tauri plugin presently uses its own Ratatui/Crossterm
versions. It therefore cannot be added to the production release by a loose
git dependency.

Before enabling `--tui` in a release, the monorepo must provide evidence for:

1. a revision-pinned dependency with a committed lockfile;
2. a real Svelte GUI and TUI rendering of the bastion profile flow;
3. focus, paste, selection, resize, alternate-screen restoration, and error
   recovery tests;
4. Windows Terminal, ConPTY-over-SSH, Linux terminal, and SecureCRT smoke
   results; and
5. one operation state/decision ledger shared by GUI and TUI.

Ratatui buffer tests are required for layout regression coverage, but they do
not replace terminal-emulator qualification.

## Native replacement sequence

1. Define the extension manifest, PX procedures, PluresDB record schemas, and
   host-effect contract in `praxis-platform`.
2. Extract the existing real OpenSSH bastion lifecycle into the narrow native
   host-effect implementation; preserve the profile migration boundary.
3. Build the Radix extension and the standalone Tauri shell from the same
   Svelte source and accepted host-effect interface.
4. Add native inventory, SSH collection, vendor identification, health,
   backup, and SNMP only when each operation has a real transport
   implementation and PX admission evidence.
5. Retire the Python/Textual/Ansible package only after data migration,
   functional parity, installer validation, and published end-of-life guidance.

No mock network results, simulated device outcomes, or UI-only operation
screens are permitted at any stage.
